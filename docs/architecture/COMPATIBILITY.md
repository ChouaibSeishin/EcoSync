## Dependency management rules

Use Boot parent 4.1.2 for backend framework/plugin management and import Spring AI BOM 2.0.2. Pin springdoc separately. Managed observations are assertions to recheck against the effective graph, not extra property overrides. Boot 4 uses newer modular starters and Jackson 3; do not copy Boot 3 starter/test or Jackson 2 customization examples without checking exact artifacts. The SDK's JSON abstraction is an explicit integration boundary.

Frontend direct dependencies use exact versions and Phase 1 commits a real application package-lock.json; use `npm ci`. The Phase 0 compatibility probe generates a separate disposable lockfile for peer resolution; a snapshot is retained as verification evidence, not as an application lockfile. Additional libraries must be researched and pinned when first introduced. No application dependency lock is claimed before an application exists. Phase 10 infrastructure/model/observability tools are not runtime dependencies in Phase 0 and get exact pins before use.

## MCP APIs and design implications

Spring AI's standard MCP client starter uses JDK HttpClient Streamable HTTP. The documentation recommends WebFlux transport for production; start with synchronous client semantics and evaluate transport scaling in Phase 3 before production commitment. Programmatic per-integration lifecycle management is needed for runtime onboarding, rather than only boot-time `connections` properties. The gateway uses `spring-ai-starter-mcp-server-webmvc` with `spring.ai.mcp.server.protocol=STREAMABLE` and SDK runtime `addTool/removeTool` APIs. Restrict authentication and endpoint exposure explicitly.

The selected SDK's source retains initialization and session-oriented transport semantics. The current specification's July 2026 revision removes protocol-level sessions and the GET stream, among other changes. This is a documented interoperability limitation of the initial target, not an assertion that the older protocol is the latest. P3-01 must prove compatible version negotiation with real servers and decide whether a coordinated Spring AI/SDK update is needed. A server requiring only an unsupported revision must fail clearly.

## Phase 1 implementation verification (2026-10-30)

The actual application uses the accepted Boot/AI BOM/Java/Node/frontend pins. [Toolchain evidence](../development/evidence/phase-1-toolchain.json) records verified Java/Node/Maven distribution hashes and official Action release commits. ArchUnit core 1.5.1 was added from its [official guide](https://www.archunit.org/userguide/html/000_Index.html) and Maven metadata for executable package-boundary tests. The Maven wrapper plugin is pinned to 3.3.4 using the [official wrapper workflow](https://maven.apache.org/tools/wrapper/).

Rechecked official [Spring Security 7.1.2 release/advisory information](https://spring.io/blog/2026/10/23/spring-security-maintenance-releases/), [CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html), [session management](https://docs.spring.io/spring-security/reference/7.0/servlet/authentication/session-management.html), [Actuator](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html) and [Testcontainers integration](https://docs.spring.io/spring-boot/reference/testing/testcontainers.html). The frontend clean install audit reported zero vulnerabilities in its 227 audited packages. This does not assert that the backend/container graphs have undergone an exhaustive vulnerability assessment. Actual build/runtime/CI results are maintained in the Phase 1 verification report. No runtime Spring AI model or MCP starter is introduced in Phase 1.

Additional maintainer advisory indexes checked during final review: [ArchUnit](https://github.com/TNG/ArchUnit/security/advisories) and [Maven Wrapper](https://github.com/apache/maven-wrapper/security/advisories) displayed no published advisories at inspection; this is not a guarantee of absence of vulnerabilities.

## Phase 2 independent source compatibility (verified 2026-10-30)

Platform dependencies remain unchanged. Supplier is a separate Node 24.22.2/npm 11.19.1 package with TypeScript 6.0.3, @types/node 24.19.2, Fastify 5.12.7, AJV 8.20.0 and development-only Swagger Parser 13.1.0, pinned exactly with a committed lockfile. [Fastify LTS](https://fastify.dev/docs/latest/Reference/LTS/) covers supported Node LTS lines; [validation documentation](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/) describes its schema contract. Publisher npm manifests were queried for the exact selected releases; Swagger Parser requires Node >=22.19, satisfied by Node 24.22.2. [Parser validation](https://apidevtools.com/swagger-parser/) runs without external reference resolution. The current npm audit returned zero advisories for this lockfile; this is a point-in-time dependency check, not an exhaustive security assessment.

Sales reuses the approved PostgreSQL 17.11 digest. Inventory uses the previously selected MySQL 8.4 LTS line at 8.4.13: [official release notes](https://dev.mysql.com/doc/relnotes/mysql/8.4/en/news-8-4-13.html), [CHECK constraint rules](https://dev.mysql.com/doc/refman/8.4/en/create-table-check-constraints.html), [account management](https://dev.mysql.com/doc/refman/8.4/en/create-user.html). The official registry index was resolved to its linux/amd64 digest and recorded in config/container-images.json. Cross-column CHECKs are table constraints. DATETIME values are UTC by explicit service/session configuration; PostgreSQL uses TIMESTAMPTZ. Real migrations, constraint tests and HTTP tests verify these choices. No JDBC/MySQL driver or MCP dependency is added to the platform.
